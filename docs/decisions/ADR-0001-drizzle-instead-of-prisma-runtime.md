# ADR-0001 — Prisma as data-model artifact, Drizzle as runtime ORM

Date: 2026-09-10 · Status: accepted for this environment

## Context
The specification recommends Prisma + PostgreSQL. Prisma's CLI and client
download native schema/query engine binaries from `binaries.prisma.sh` on
first use. In the build environment (and some locked-down enterprise
networks), only the npm registry is reachable; the Prisma CDN is not, so
`prisma generate`, `db push` and `migrate` cannot run. No Prisma engine
binaries are redistributed via npm packages.

## Decision
1. `apps/api/prisma/schema.prisma` is delivered and maintained as the
   canonical **data-model specification / ERD artifact** (deliverable 3),
   written in Prisma schema notation with all entities, enums, indexes and
   constraints described.
2. The executable implementation uses **Drizzle ORM + drizzle-kit**
   (pure TypeScript, npm-distributed, no binary downloads) over the same
   PostgreSQL 16 schema: `apps/api/src/db/schema/*`.
3. Migrations are SQL generated by drizzle-kit plus a versioned, hand-written
   `constraints.sql` for objects neither ORM expresses (`btree_gist` temporal
   exclusion constraints, immutability triggers).
4. No architectural decision depends on the ORM: repositories/ports pattern
   keeps services independent, and in a normal network environment a
   migration back to Prisma is a mechanical 1:1 mapping (the Prisma schema is
   kept in sync).

## Consequences
- Positive: works offline/firewalled; full control over exclusion constraints;
  smaller dependency footprint.
- Negative: two schema notations to keep in sync until standard environments
  adopt Prisma; a CI check (`scripts/check-schema-sync.md` guidance in docs)
  compares table/column lists between the two before merges.
- PostgreSQL remains the canonical store; all engineering rules
  (server-authoritative money, temporal availability, immutable ledger) are
  unchanged.
